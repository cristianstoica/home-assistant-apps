Timezone Correction

Retrospective timezone correction rebuilds a site's entire timezone-derived history under a different zone. It runs as a background job in chunks and can take a long time. Nothing changes for readers while it builds — the site keeps serving its current published history until the rebuild finishes and flips.

What the flip changes, permanently:

  • The site's timezone becomes the new zone.
  • Every daily-truth day and every forecast/observation pair is re-derived on the new local-day boundaries, so day-level scores change.
  • The previous generation is retired and its derived rows are deleted in the background. That deletion is housekeeping — the site's history is already correct without it. If it stops before finishing, the panel says so.
  • Raw forecast samples and raw observations are not deleted, so a correction made with the wrong zone can simply be corrected again.

What happens to verification runs:

  • Runs that were already published keep rendering. A published run is a self-contained snapshot and is unaffected on the Verification page.
  • They can no longer be re-derived. A published run's input fingerprint was computed over the daily-truth rows of the generation it ran on; once those rows are deleted, that fingerprint can never be recomputed and checked against live data again.
  • Expect the site's published run to be flagged "stale inputs" straight after the flip. This is correct, not a fault: the run was computed on the previous generation. The flag clears when the next nightly run publishes under the new generation.
  • If a nightly verification run happens to be running when the rebuild flips, that run will normally fail, and the Verification page will say "A newer verification attempt failed; the results below are from the last successful run." This is expected, not damage the correction caused: the run was pinned to the generation it started on, and the flip changed that pinning underneath it. The last successful run keeps showing, and the next nightly run publishes normally under the new generation.

If it goes wrong: start another correction with the right zone. The data it derives from was never deleted. There is no way to cancel a correction once it has started. A correction can also fail before it publishes — if it does, the panel says so and names the generation; nothing was published, and you can start another one. Separately, a correction that published successfully can have its background cleanup stop. The panel says so too. That one is not a data problem — the site's history is correct — it only means the previous generation's rows were not reclaimed and the database is larger than it needs to be. Starting another correction clears them.
